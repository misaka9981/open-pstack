### Autopilot-stack

**You own the stack, never the landing. Hand the operator one linear stack of base-chained PRs to review and land.** **Autopilot-full** holds except for how verified work leaves. Each tick re-reads both playbooks from disk under the installed plugin, and this one wins where they differ.

1. **Run Autopilot-full's owners, minus the landing.** Owners report STACK-READY in place of merge-ready. They never rebase onto another branch, trunk included, and never retarget, merge, close a PR, or arm auto-merge, because the root owns the chain's topology and the operator owns the landing. When an item depends on another, its owner branches from that item's branch, not from trunk. When the head repository is a fork, validate its identity and record its owner and repository name as `<fork-owner>` and `<head-name>`.
2. **Give the topology one writer.** Owners push only their own branches and report each tip, its current patch base, and its intended parent. Only you rebase or retarget a link, because two writers on one chain undo each other. Before you rebase, force-push, or retarget an existing PR, apply Shipping step 4's disarm-and-confirm rule to that PR and every descendant, stopping if the forge cannot confirm every request off. Fetch trunk through `<base-remote>`. Fetch another stack branch directly through `<head-url>`, because `<head-remote>` may have the base repository as its fetch URL and the fork as its push URL. Validate the chosen repository identity through the active forge, and record the fetched target as `<parent-tip>`. Before rebasing, record the child branch's published SHA as `<captured-sha>` with `git ls-remote -- "$head_url" "refs/heads/$branch"` and require it to equal the local pre-rebase tip. Require `git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` to pass. When the parent changed, move only the child's commits with `git rebase --onto "$parent_tip" "$current_base_sha" -- "$branch"`, then record `<parent-tip>` as the child's new patch base. Publish with `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"`. An owner takes your push as its new base and lease, and on a conflict resolves its own slice for you to push.

   Append each clean PR in dependency order to one frozen bottom-to-top list. When the head and base repositories are the same, set its base to its parent's branch, so the forge's base-branch chain also records the order. Use `origin pr create --status open --base "$parent_branch"`, `gh pr create --base "$parent_branch" --repo "$base_repo"`, `origin pr edit "$pr" --base "$parent_branch"`, or `gh pr edit "$pr" --base "$parent_branch" --repo "$base_repo"` according to the resolved forge and operation. When the head repository is a fork, keep the local child branch rebased onto its parent's exact tip but create or retarget every PR against `<trunk>` in the base repository, because a forge cannot use a fork-only parent branch as a PR base. With GitHub, capture the approved PR title and body as `<title>` and `<body>`, then create it with `gh api --method POST "repos/$base_repo/pulls" -f "title=$title" -f "body=$body" -f "head=$fork_owner:$branch" -f "head_repo=$head_name" -f "base=$trunk" --jq .html_url`, adding `-F draft=true` only when Opening a PR's readiness rule requires a draft. Retarget it with `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"`, or use the resolved Origin equivalent for either. For fork heads, never infer stack order from their equal base branches. Never require `gt`.
3. **Absorb drift at the root.** Until landing starts, apply Autopilot-full step 5's test to each link and rebase the chain bottom-up where it calls for one, with step 2's explicit old-base and new-parent flow. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and you push the result using step 2's captured-SHA lease flow. Then apply the patch ID rule link by link to each PR's recorded patch-base-to-head diff at its verdict SHA and its new one, since a link's base is its parent.
4. **Deliver the chain, then keep your hands off it.** Each link carries its verdict in its PR. The operator sends only the current bottom PR through Shipping, one at a time. Merge-when-ready applies only to that bottom, after Shipping has disarmed and confirmed every descendant, so never offer or arm it for the chain as a whole or for a descendant. Once landing starts, nobody writes to the chain except the post-merge move that `playbooks/shipping.md` sanctions, because a second writer breaks a landing in flight. A mid-landing problem goes through you to the operator, and any fix waits for the operator's go.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
