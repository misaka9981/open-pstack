### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.**

1. **Resolve the forge, then verify each PR independently before it lands.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for PR view, watch, and edit operations, and for merge only when step 4's expected-head guard is available. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`).

   Record the forge-reported base repository as canonical `<base-repo>`. On GitHub, split it into `<base-owner>` and `<base-name>`, pass `--repo "$base_repo"` to every `gh pr` command, and pass the two components to the GitHub watcher. Resolve `<head-remote>` from the branch's configured push remote, `remote.pushDefault`, branch remote, or sole unambiguous remote, in that order. Confirm its push URL names the PR head repository, and record that exact URL as `<head-url>` so the captured remote state and the guarded push address the same repository. Resolve `<base-remote>` independently by matching a fetch URL to `<base-repo>`, and confirm that URL before using it for trunk. The same remote name may fill both roles when its push URL matches the head repository and its fetch URL matches the base repository. Compare each URL by role instead of assuming the remote name identifies one repository. Capture every resolved or forge-reported value directly into a shell variable. Command examples use quoted lower-case variables such as `"$branch"` and `"$head_url"`. Never paste those values into shell source, and never guess or treat the forge name as a Git remote.

   Freeze an explicit bottom-to-top PR list. Confirm a same-repository stack against its base-branch chain. For fork heads, take the order from the verified local parent ancestry, because every PR targets trunk and the forge bases do not encode the stack. Before launching any verifier, disarm every PR in the list and confirm it, because an armed request lands whatever head is ready, verdict or not. On GitHub, query each PR through GraphQL for `id`, `headRefOid`, `baseRefName`, `autoMergeRequest`, and `mergeQueueEntry`. When `autoMergeRequest` is non-null, run `gh pr merge "$pr" --disable-auto --repo "$base_repo"`. When `mergeQueueEntry` is non-null, invoke the `dequeuePullRequest` mutation with `gh api graphql -F "id=$pr_node_id" -f query='mutation($id:ID!){dequeuePullRequest(input:{id:$id}){mergeQueueEntry{id}}}'`. The mutation takes the pull request node ID. Re-query and require that both `autoMergeRequest` and `mergeQueueEntry` are null, because one can be null while the other is not. On Origin, use its reported cancel operation and inspect every separately reported queue state. Stop if the active forge cannot confirm the whole list is unarmed.

   One subagent per PR verifies it, each a background subagent in its own worktree. It runs the change the way a user would with the matching driver skill (`run` for CLIs and TUIs, `verify` for UIs), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. The bottom PR's parent is trunk. Each child's parent is the preceding PR's exact head, including when a fork child targets trunk at the forge. Only a verdict from an agent that did not write the code counts, because an author checks what it meant to build. Green CI and an approving bot review are not verdicts, because neither runs the change as a user would.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because it cannot land without the code below it. One whose branch neither holds nor needs that code can move onto trunk and land on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. At the passing verdict, record `<verdict-sha>`, `<verdict-base-sha>`, and the stable `<verdict-patch-id>` of `<verdict-base-sha>..<verdict-sha>`, and start `<landing-sha>` and `<landing-base-sha>` at those head and base values. Do not replace a fork child's patch base with its forge base, because that forge base is trunk and includes its unmerged parents. Before trusting an older verdict, read the current published head through the active forge as `<current-head>`, require the local branch tip to match it, and compare the stable patch ID of `<landing-base-sha>..<current-head>` with `<verdict-patch-id>`.

   When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files, so a reader can check the call. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted. When the patch did not change, keep the verdict, set `<landing-sha>` to `<current-head>`, and re-run mergeability and CI at that head. Keep both SHAs, because a patch-equivalent rebase makes them differ. Never use matching commit messages or a green check from an older SHA as a substitute.
4. **Land bottom-up, one PR at a time.** Before touching a branch or base, inspect the current bottom and every descendant through the active forge, because another actor can rearm a PR after verification. On GitHub, repeat step 1's GraphQL query, disable each non-null `autoMergeRequest`, dequeue each non-null `mergeQueueEntry`, and confirm both fields are null for every PR. On Origin, use its reported cancel operation and inspect every separately reported queue state. Stop before any rebase, force-push, retarget, arm, or merge if the active forge cannot disarm and confirm every PR in that set.

   Always merge the run's lowest unmerged PR. On Origin the plain command also merges every PR below the one you name, and on GitHub a PR whose base is still its parent's branch merges into that branch, not trunk. Immediately before any merge or auto-merge request, read the current `headRefOid` and `baseRefName`. Require that `headRefOid` equals `<landing-sha>` and `baseRefName` equals `<trunk>`, the recorded `<landing-base-ref>`. That read is a preflight, not a lock, so every merge also needs a server-enforced expected-head guard. Run the GitHub merge immediately after the matching preflight with `gh pr merge "$pr" --squash --match-head-commit "$landing_sha" --repo "$base_repo"`. GitHub has no server-enforced expected-base precondition, so keep watching `baseRefName` and verify the merged base in step 5 instead of inventing a guard. Origin has no documented expected-head option. Run `origin pr merge "$pr"` only when the active server reports that guard, and otherwise fall back to a resolvable forge that supplies it or stop before merging. Read the PR back for the result (`origin pr view "$pr"` or `gh pr view "$pr" --json state,mergedAt,baseRefName --repo "$base_repo"`), because a merge command can report success when a merge queue only queued the PR, and a requested auto-merge is not a merge. A landed PR reads merged with trunk as its base, not its parent's branch.

   Arm `--auto` (Origin merge-when-ready or GitHub auto-merge) only on a PR whose verdict covers its current head, because it lands whatever head is ready. Arm it only when the repository has a required, SHA-scoped verification check for the independent verdict that goes unsatisfied on every head update. On GitHub, run `gh pr merge "$pr" --squash --auto --match-head-commit "$landing_sha" --repo "$base_repo"` immediately after the matching preflight, and treat a non-null `mergeQueueEntry` as an armed request. Without that check, keep watching and run the guarded merge when the PR becomes ready.

   After a merge lands, fetch trunk through `<base-remote>`, confirm the merged SHA is present, and drop the merged PR from the frozen list. Then move the next PR onto the merge result. Retarget it to trunk when its base was the merged branch (`origin pr edit "$pr" --base "$trunk"` or `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"`). Re-read `baseRefName` after any retarget and require it to equal `<trunk>`. Record `<trunk>` as `<landing-base-ref>`, separate from the commit-valued `<landing-base-sha>`. A fork child already targets trunk. The next PR's `<landing-base-sha>` is still its former parent's exact tip, and a host's automatic retarget does not change that. Move its patch with the guarded rebase below, then let step 3's patch ID rule decide whether the verdict survives, because the verdict covers the patch, not its commits. Merge it once its checks pass and its verdict survives.

   The guarded rebase moves only this PR's commits. Fetch current trunk through `<base-remote>` and record its exact tip as `<trunk-tip>`. Record the published SHA with `git ls-remote -- "$head_url" "refs/heads/$branch"` and require that `<captured-sha>` to equal the local pre-rebase tip. Require `git merge-base --is-ancestor "$landing_base_sha" "refs/heads/$branch"` to pass. Move the commits with `git rebase --onto "$trunk_tip" "$landing_base_sha" -- "$branch"`, set `<landing-base-sha>` to `<trunk-tip>`, and publish with `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"`, never a bare lease or plain force. Then repeat step 3's current-head check and patch comparison.
5. **Leave the stack alone while it lands.** Step 4's move of the next PR is the only change to a branch or base, because a merge lands whatever its branch and base hold at that moment, verdict or not. On GitHub, run the queued watcher from `playbooks/babysit.md` (`skills/poteto-mode/scripts/watch-pr/watch-pr --owner "$base_owner" --repo "$base_name" --queued-stack --stack-prs "$run_prs"` under the installed plugin, with the run's PRs bottom to top) under `/loop` in dynamic mode until it reports `COMPLETE` at the ceiling. Use it only as an event wake. After each wake, poll the current bottom with `gh pr view "$pr" --json headRefOid,baseRefName,state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest --repo "$base_repo"` and step 1's GraphQL query for `mergeQueueEntry`. On Origin, re-read the current PR's head, base, merge-when-ready state, and queue state with `origin pr view "$pr" --checks --comments` each time `origin pr checks "$pr" --watch` returns, until the ceiling reads merged.

   Before accepting checks, a queue entry, or a merge, require that `headRefOid` equals `<landing-sha>` and `baseRefName` equals `<landing-base-ref>`. On any head or base change, disable or dequeue every pending request, stop the watch, and return through step 4 to step 3, re-running CI and mergeability even when the patch ID is unchanged. A PR that merged at another head or into another base is a safety failure, so report it and do not continue the stack. If the bottom becomes mergeable while both `autoMergeRequest` and `mergeQueueEntry` are null, return to step 4 and merge it. Treat the bottom as landed only when `mergedAt` is non-null or `state` is `MERGED`.

   A descendant whose base moves to trunk when its parent merges is expected, not damage to repair. Hard-fail when the bottom reads `CLOSED` with no `mergedAt`, or when a required check reaches any terminal, non-passing conclusion, regardless of whether auto-merge or a merge-queue entry is pending. Disable or dequeue every pending request before you diagnose. `UNSTABLE` is not a failure by itself, so judge completed checks by whether they are required. `BLOCKED` while checks are pending, auto-merge is armed, or a queue entry exists is not a failure. When `mergeStateStatus` is `DIRTY`, or `BEHIND` blocks landing, disarm, return to step 4's guarded rebase and step 3's re-verification, and stop on a conflict you cannot resolve. Do not use Babysit's queued `WAITING` or `merge-queue` stop condition here. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what landed and how you confirmed it, and what the next gap needs.
